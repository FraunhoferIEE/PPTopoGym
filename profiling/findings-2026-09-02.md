## Where a 23 ms step goes (pandapower backend)

Every step runs **two full AC power flows** by design (reward at index k, next observation at
k+1: `gym_env_pp.py:870` and `create_observation` → `run_pf` at `simulation_env.py:931`), and
each AC solve is preceded by a DC power flow for angle init (600 `_run_dc_pf` calls / 300 steps
under cProfile).

| component (measured directly, no profiler) | ms | share of 23.4 ms |
|---|---|---|
| `run_pf` × 2 | 18.1 | 77% |
| `create_observation` (full, cached results) | 0.77 | 3% |
| `observation_to_info` × 2 (before/after) | 0.52 | 2% |
| `calculate_reward` | 0.03 | — |
| `load_profile_timestep_into_net` | 0.10 | — |
| `load_action` (topology) | 0.01 | — |
| unattributed (gym plumbing, post-topology cache rebuilds, info dict) | ~3.9 | 17% |

Inside `run_pf` (cProfile shares of the pf cost): NR solve wrapper (`newtonpf_new`, includes
the C++ solve) ~44%, `_pd2ppc` ~23%, `_extract_results`/`_ppci_to_net` ~17%, the DC init pf
~9%, `init_results` ~6%. `_get_switch_results` alone is ~0.6 s / 300 steps (~2 ms/step-pair)
building `res_switch`, which nothing in the env reads (only `save_state`/parallel N-1 copy it).
All of this is **pandapower-owned** — fixable only by calling it less or not at all.

Env-owned code is ~1.5 of 23.4 ms. The line profile (`mix_lines.txt`) puts the biggest
env-owned cluster in `_fill_nan` (`simulation_env.py:157-158`): ~28 calls/step,
~150 µs/step traced (real is less; the 0.4-0.6 µs/line entries are tracer floor).
Not worth touching while a step is 77% power flow.

## Optimization candidates, ranked by absolute saving per weighted step

1. **Run the step path on `backend="lightsim"`** (`env_config["backend"]`, already wired on
   this branch, N-1 included). Measured: **22.6 → 5.4 ms/step, ~3.9×**, same 14 crashes on the
   same steps. Tolerance-gated (~1e-11 parity), not bit-identical — opt-in per workload, as
   already documented. This dwarfs everything else; the remaining items are what's left *after*
   it.

2. **Skip the redundant DoNothing re-solve** at `gym_env_pp.py:870`. `load_action(0)` returns
   early preserving `net.converged=True` and the res tables from the previous step's
   observation solve — same topology, same profile index — yet `step` calls `run_pf()`
   unconditionally and re-solves the identical state. Guarding on `net.converged is True`
   is bit-identical by construction (the tables are literally the ones already on the net).
   Saves one full pf on 30% of steps: **~2.7 ms weighted (~12%)** on the pandapower backend,
   ~0.5 ms (~9%) on lightsim. Check the reset path leaves `converged=True` (it does — reset
   solves and builds the first observation) and that `restore_state(run_pf=False)` callers
   aren't affected.

3. **Stop rebuilding the six `res_*` DataFrames per lightsim solve**
   (`toolbox/ls2g_backend.py:485,503,528,543,554`). 586 solves × 6 `pd.DataFrame(...)`
   constructions = ~0.9 s of the 3.3 s lightsim cProfile (~27%); with a fixed net the shapes
   and indices never change, so the frames can be allocated once and refilled through cached
   `.to_numpy()` column views (same trick as `load_profile_timestep_into_net`). Order of
   ~1-1.5 ms/step on the lightsim backend — the single biggest post-lightsim item. Also
   `_write_bus_lookup` (`ls2g_backend.py:438`) is a per-bus Python dict loop, ~110 µs/solve,
   vectorizable.

4. **Cache `_grid_is_disconnected`** (`gym_env_pp.py:808`): runs on every `run_pf`
   (~0.2-0.35 ms × 2/step) though the answer only changes when topology changes — key it on
   the same fingerprint the observation cache uses. ~2% pandapower backend, ~7% lightsim.

5. **DC-init elimination on the pandapower backend** (`init` in the warm options): each AC
   solve pays a ~0.8-1.5 ms DC pf purely for the NR starting angles. `init="results"` (warm
   start) would drop it and likely cut NR iterations, but changes the starting point, so it is
   tolerance-gated like the ls2g backend, *and* it interacts with the
   `net["_ppenv_warm_options"]` key (`init_vm_pu` is part of it for bit-identity). Only worth
   doing if the step path stays on the pandapower backend.

## Measured and ruled out

- **Action application**: `load_action` is ~10 µs — the positional-write optimization has
  closed this; DoNothing vs topology steps differ by <0.5 ms (that difference is the
  post-topology observation-cache rebuild, already content-fingerprinted).
- **Reward, profile loading, info plumbing**: all ≤0.1 ms/step.
- **Env-owned observation micro-costs** (`_fill_nan`, the per-key dispatch in
  `_get_default_observation`): ~0.5-1.5 ms/step total across ~50 keys × 3 passes
  (before/after/full). Only becomes relevant after item 1; even then items 2-3 pay more.
- **`newtonpf_new` at 12 ms/call in cProfile** is profiler inflation on a hot wrapper, not a
  regression — the untraced `run_pf` is 9.0 ms, matching the ledger.
- The two-pf-per-step structure itself is env semantics (reward at k, observation at k+1),
  not waste — except for the DoNothing case in item 2.

## Tool note (withlineprofiler 0.8.3)

Line attribution excludes most time spent inside non-project callees: `_on_return` fires for
*every* Python frame's return and clears the pending line, so a project line that calls into
pandapower is only billed until the first pandapower-internal function returns
(`profiler.py:_on_return` has no `_admits` check). That is why `_powerflow(net)` shows
8.5 µs/hit against a real ~9 ms. Treat `mix_lines.txt` as env-owned cost only; the
pandapower-side split above comes from cProfile.
